# 大量已完成任务的看板加载

## 故障原因

列的十张卡片预算只限制了卡片，日期、文档和其他分组标题仍全部进入 DOM。后续日期留下展开但空白的分组，撑高列的滚动高度，使接近底部判断无法及时继续加载。组合板按文档分组的 `autoFill` 又绕过了接近底部判断，持续在后台填满列。列局部替换后，旧列体上的滚动监听还会失效。

## 沿用的架构

数据仍由 TaskStore、任务索引和原来的文档读取流程管理；没有复制一个已完成任务库，也没有改变完成状态、归档规则或笔记内容。看板使用自己的列任务窗口，独立于清单的 `listRenderLimit`。

- 展开的未来分组在第一张卡片进入窗口时才显示，避免空标题撑高滚动区域。折叠分组保留标题，组内卡片首次展开时再渲染。
- 普通看板和组合板都按可见列及列底部的位置续载，不再强制填满文档分组。
- 滚动监听在稳定的看板容器上捕获，列被替换后继续有效；取消任务时注销监听。
- 完成日期的分组及排序在本次投影视图内复用，组合板的活动分组只准备一次。
- 列窗口记录已挂载完整子树的卡片数量。后续批次使用短占位游标复用原有卡片，只装饰和解析新增卡片；部分加载的父任务继续递归。投影失效时交给现有重建路径，折叠状态变化清除子树计数。该状态随列加载器释放，不保存任务副本或脱离页面的 DOM。
- 增量合并失败时从同一投影生成完整窗口作为一致性回退；正在编辑的已挂载节点和正常续载时的滚动锚点保留。

## 验证

`node scripts/kanban-large-column-browser.test.js` 使用实际运行时代码和 CSS，覆盖已完成/未完成、普通/组合板、10,000 条任务、1,000 张卡片后的批次开销、209 条跨日期任务完整续载、列替换、折叠首次展开和手机宽度。清单窗口固定为 1，检查续载不受其影响。`--baseline` 使用 Git HEAD 中的原版运行时重现问题。结果保存到 `output/playwright/kanban-large-column-before.json` 和 `kanban-large-column-after.json`。

## 万条规模的边界

该修复减少初始 DOM、后台持续渲染、重复卡片装饰和 HTML 解析。原来的 TaskStore 投影仍需读取并筛选完整文档范围，列遍历也保留原有规则；并非服务端逐页查询。当前任务索引单文档读取上限为 20,000，总 SQL 上限为 500,000。

持续向下浏览会累计保留已加载卡片，因此不能把 10,000 条候选数据的测试解释为“10,000 张复杂卡片同时挂载也无开销”。若要在全部历史记录的深度浏览中保持 DOM 上限，下一步应在现有列窗口适配器中实现可回收窗口及高度占位，并处理父子树、折叠、拖放、正在编辑的卡片、跳转定位及滚动恢复；不能仅提高批次大小或查询上限。当前回归验证的是加载正确性和增量工作量。
