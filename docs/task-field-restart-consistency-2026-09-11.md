# 任务字段重启一致性排查（2026-09-11）

## 结论与证据边界

这不是只影响状态拖拽或优先级的单点问题。源码和隔离行为测试确认了以下共性缺陷；尚未在反馈用户的思源进程中复现关闭、重启全过程，不能把所有反馈都归结为真实数据丢失。

1. 普通字段修改进入公共队列时，只有显式传入 `persistSnapshot: true` 才安排启动快照保存。许多非拖拽入口没有传入，因此内核已提交不等于启动缓存已更新。
2. 启动原始数据签名主要比较 ID、正文、更新时间、文档；首屏刷新指纹也遗漏了优先级、状态、备注等属性。同一时间戳下只改属性，可以被误判为未变化；即使数据重读成功，也可能没有重绘。
3. `normalizeTaskFields` 中旧 MetaStore 回填不尊重字段已读取标记。清空优先级、时长、备注、日期颜色、完成时间、循环字段，或修改置顶、里程碑、全天置底，都可能被旧缓存恢复。专注次数的缓存合并也遗漏了已读取标记。
4. 自定义字段存在更严重的反向写入：旧版本在已有原始属性 `project = new`、缓存为 `project = old` 时，实际排队了 `custom-field-attr-backfill`，补丁为 `project = old`。这是可导致旧值重新写入的路径，不仅是界面显示问题。

第 4 项使用旧提交中的真实归一化、回填函数和写入队列替身验证，没有向真实笔记写数据。修复后，已读取的空值、新值均不能被该回填覆盖；未加载字段仍保留原有兼容回退。

部分加载时也禁止把未读取的字段当成缺失字段自动写回。已成功读取的块属性是权威来源；若历史任务从未将字段写入块属性、仅保存在 MetaStore，需要单独核验迁移，不能用无法判定新旧的缓存自动覆盖。本修复不删除 MetaStore 中的历史数据。

## 检查范围

| 字段或操作 | 检查与处理 |
| --- | --- |
| 正文、Markdown、完成状态、状态标记、自定义状态、优先级 | 检查 contentPatch、setDone、taskPatch；公共提交默认保存；补齐指纹；完成状态专用命令透传选项 |
| 开始日期、截止日期、自定义时间、完成时间、日期颜色 | 检查日期适配器、详情、看板时间拖拽、甘特、日历；删除详情不必要的跳过保存；日历仅延迟视图更新 |
| 备注、时长、置顶、里程碑、全天置底 | 已读取的空值/布尔值优先于旧 MetaStore |
| 番茄分钟、小时、实际次数、预估次数 | 纳入完整字段校验；已读取的次数清空不再被旧缓存恢复 |
| 循环规则、循环状态、完成历史 | 检查普通修改、推进、撤销历史、原生完成复位；复合操作中间状态不保存，最终完成后安排快照 |
| 自定义字段 | 检查部分加载、全部加载、清空和回填；区分未读取与已读取但不存在；禁止旧缓存覆盖已读取值 |
| 附件路径、附件元数据 | 检查公共队列、快照往返、空值保护；加入字段注册表和启动指纹；保留原有附件属性快照保护 |
| 文档归属、父子关系、标题分组、顺序 | 检查结构移动提交、结构快照、往返及原有契约测试；原有结构提交已安排快照，不改为普通字段快照 |
| 白板坐标/连线、视图设置 | 独立存储及现有批量保存回归；不属于任务属性快照，不套入字段提交策略 |

优先级得分、剩余时间、子任务计数等计算结果不应独立保存为用户字段，其输入字段已纳入检查。专注插件、跨设备同步和宿主强制退出的实际时序，需要独立现场验证。

## 修复原则

- 在确认提交后，普通字段默认安排快照维护；乐观更新和回滚不会因此新增快照写入。
- 保留显式 `persistSnapshot: false`、`skipSnapshotPersist: true`，供只做镜像确认等内部路径使用。
- `deferProjection: true` 默认仍保护复合操作中间状态；明确的 `deferSnapshot: false` 才允许视图自己刷新、提交照常保存。
- 复用原有合并、空闲调度和按文档池保存机制，不在每次字段编辑时同步序列化整棵任务树。
- 按字段注册表建立指纹，比较 SQL 原始值及归一化值；原始 SQL null/空字符串不能退回到旧别名。
- 结构化字段采用稳定键序；正文中看似 JSON 的文本仍按原文比较。
- SQL 未启用的循环/专注属性占位列不标记为已读取，避免把延迟加载误当成用户清空。

主要实现：`09-task-field-schema.js`、`32-runtime-state-and-events.js`、`53c-document-loader-runtime.js`、`30-dialogs-and-ui-foundation.js`，以及 `10-stores-rules-and-cache.js` 和 `40-render-runtime.js`。

## 为什么开发机可能不复现

这是有条件的缓存和时序问题，不是每次修改都会失败。开发机可能没有命中旧快照，或启动走了完整加载；测试期间更新时间、任务顺序、正文、文档范围变化也可能碰巧触发旧代码的刷新条件；后台写入、重读已经完成时同样不会表现异常。旧 MetaStore 内容不同，也决定了能否触发反向回填。

新建任务后恢复正确，与失效缓存/漏刷新的机制相符，但不能单凭现象认定宿主磁盘数据已经丢失。此前仅从拖拽入口补保存标志，不足以覆盖这些公共路径。

## 验证与限制

- `scripts/task-field-startup-cache-behavior.test.js`：真实签名、队列定义、提交调度、首屏校验函数；相同时间戳属性变化、普通完成、显式跳过、复合事务保护。
- `scripts/task-field-cache-authority-behavior.test.js`：真实归一化与元数据合并/回填函数；清空、开关、循环、专注次数、部分加载、自定义字段禁止旧值写回。
- `scripts/task-snapshot-pool-behavior.test.js`：全部注册字段的有效值快照往返，以及原有保存合并、写失败、读取版本和容量保护。
- 全量运行 `scripts/*.test.js`；拼接清单中的 56 个脚本做语法编译，并单独检查 `calendar-view.js`。

测试包含隔离替身及静态契约，不等同于真实思源关闭重启测试，也不证明任意断电/杀进程都能保存尚未确认的写入。没有打包发布，也没有修改真实笔记。

## 现场复核

在测试文档中分别修改/清空各字段并正常退出重启，同时覆盖普通任务、循环任务及有旧缓存的工作区。若仍异常，先记录任务块 ID、插件/思源版本和对应块属性，保留当时缓存与日志，再手动刷新；不要先新建任务破坏现场。

- 块属性已经是新值、界面仍旧：继续查启动缓存、归一化和刷新。
- 块属性仍旧：查写入是否已经确认、失败日志、旧值回填或外部同步覆盖。
- 尚未收到确认就终止进程：属于未完成写入边界，不能靠保存派生快照保证宿主数据落盘。
- 正文、备注等仍处于未提交编辑状态的草稿，需要与已确认的字段修改分开复核，不能用这次快照修复承诺草稿在强制退出后不丢失。
