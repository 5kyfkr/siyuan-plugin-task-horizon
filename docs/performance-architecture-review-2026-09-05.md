# Task Horizon / PINCH 读写与快照架构对比

## 范围与结论

检查本机 PINCH 2.6.5 的发布代码、当前 Task Horizon 源文件及本机思源 3.8.2 源码。PINCH 目录为 `C:/Users/y5213/Cloud/data/plugins/pinch`，思源目录为 `D:/AI/trae/siyuan3.8.2`。PINCH 仅只读分析，没有加载其前端代码执行真实操作，没有修改插件或用户数据。

PINCH 的轻量索引、按视图选择数据详细程度、请求合并、局部更新和部分列表的可见窗口渲染，能够解释其较低的交互工作量；不能仅凭静态分析证明其在相同数据集下必然更快，也没有得出 CPU、内存或帧率的实机数值。

## PINCH 值得借鉴的机制

| 机制 | 安装代码依据 | 对 Task Horizon 的意义 |
| --- | --- | --- |
| 内核轻量索引 | `kernel.js:58`，内存 Map；30 秒内命中缓存，超过后尝试增量；上次全量超过 5 分钟时在访问时全量刷新 | 减少前端反复处理完整任务树；不是要求每次插件启动全量重建 |
| 需求分级与请求合并 | `index.js:93`，`getBlockTasks` 区分 light/full，共享全局及范围 in-flight promise，用 generation 拒绝过时结果 | 继续复用现有 TaskStore、字段加载计划和增量更新，不另建平行状态管理器 |
| 日期范围和可见项补全 | `index.js:2573`、`index.js:2591`，按视图选择数据；`index.js:2568`，只为可见任务补全标题，单批上限 120 | 将非首屏必要的信息留到实际使用时再取 |
| 滚动可见窗口 | `index.js:2568`，部分未分组看板及时间线按起止位置 slice，并用上下留白维持滚动高度 | Task Horizon 某些列表目前是累计增加渲染行数，不能等同于只保留可见行的窗口化 |

PINCH 内核的隔离探针用模拟 API 验证：首次读取走全量，30 秒内命中不发 SQL，超过热缓存期限走增量，超过全量期限走全量。探针不访问真实思源数据，不是性能跑分。

## 不应照搬的部分

- 内核增量刷新仍检查全部已缓存 ID 的存在性，并非纯粹只访问变化项。
- 日期范围接口先取得轻量索引，再在内存中过滤；日历还可能同时取基础轻量集合，不能说所有日期视图都只扫描日期范围内的 SQL 行。
- 5000 条是内核快路径上限；前端全量兜底仍可扫描到 20000 条。不能通过降低 Task Horizon 的数据完整性制造更快的假象。
- `index.js:25`、`index.js:167` 使用 localStorage 保存完整任务缓存，JSON 处理仍是同步操作；不适合直接搬入 Task Horizon 的大容量多范围快照。内核索引本身没有对应的落盘快照。
- 内核范围 Map 未观察到淘汰逻辑；不能据此宣称 PINCH 不存在任何内存增长风险。
- `index.js:201` 的 `updateTask` 分别写属性和任务标记。Task Horizon 的内核任务写入组合事务并直接验证结果，不能为省时间退化为两个缺乏联合验证的写请求。
- 思源 `kernel/api/transaction.go` 在事务 API 返回前等待提交；`kernel/sql/block.go` 的 GetBlockAttrs 实际读取 IAL 缓存或树，不应误判为滞后的普通 SQL 查询。Task Horizon 原有写入确认与必要的 SQL 队列屏障应保留。

## 本轮落地范围

1. 三个派生缓存共用每文件串行锁及严格读取/恢复语义，保留独立文件与现有服务边界。
2. 文档范围缓存改为有界 pending Map，消除防抖仅保存最后一个范围、并发写入丢更新、延迟压缩回写旧数据的问题。
3. 快照去重直接取实际打包记录及引用内容，覆盖日期颜色、文档信息、辅助块和视图数据；不再维护一份易漏字段的签名列表。
4. 当前范围打包一次；无变化跳过整库构建，变化只构建一次；冷加载不再为了压缩判断而额外序列化完整文件两次。
5. 损坏 JSON 先备份再允许重建；不可用不等于空文件。读取有取消期限，写入不因超时歧义自动放锁重试。
6. 索引与快照复用 TaskStore 读取版本，防止异步读盘期间发生任务变更后仍保存旧投影；失效后的异步结果不得复活旧内存缓存。

行为回归使用 20 个范围共享一份 500 任务文档：加载期间完整非空快照库容量序列化次数为 0，共享文档容量测量为 1 次。保存回归验证无变化整库构建为 0 次、发生变化为 1 次。它们衡量的是工作次数，不是实机耗时或 CPU 百分比。

## P0 / P1 / P2 实施补充

- P0：复用字段更新及原有行模型，为清单顶层叶子任务增加完成状态的节点保留、单行移除及同组移动。完成投影不会将已经加载的渲染窗口重置到初始页；锚点支持邻行接替。父子级联、跨组、新分组及未挂载行补入仍保留结构协调回退，不承诺任意操作都不重建。
- P0 后续刷新：普通清单原有整段替换改为与紧凑卡片共用节点协调，无分组清单也进入同一路径。权威读取完成后仍保留未变任务，而不是只优化勾选当下。测试还限制组头更新时的无效节点移动次数。
- P1：权威文档刷新及已解析文档的属性变更标记脏文档，合并延迟保存。每个变更文档只打包一次，更新兼容范围引用，不展开未变文档；新建补偿也复用此路径。旧水位、读取失败、截断结果及容量裁剪都有保护，未变文档不会因局部保存延长整个范围的新鲜期。
- P2：四个任务读取入口统一在途合并，不新增持久结果缓存；参数、读取粒度、配置及版本隔离，结果分离给各消费者。SQL 合并保留原并发队列，并用 Promise 身份检查防止旧请求清除新请求；缓存拒绝过时代际和 TaskStore 版本的回填。删除事务让读取过期时不再向加载层抛出“请重试”，由已有的加载 token 校验丢弃旧状态提交。
- 新行为测试覆盖：60 行清单的节点身份及窗口保留、锚点被移除后的邻行接替、同组单行移动；20 范围共享文档只打包一次；两文档连续变更合并一次保存及失败后再合并；并发读合并、不同参数隔离、过期拒绝、消费者结果隔离及 64 项上限。这些是工作次数和逻辑行为验证，不是实机帧率或 CPU 降幅测量。

## 保留边界与下一步

- 不每次启动重建快照：先校验并使用可用缓存，缺失、过期、版本不兼容或引用损坏时回到既有加载流程重建对应范围。
- 本轮没有改 Vue、引入 Worker/新数据库、改成 localStorage，也没有改变任务事务与写后验证。
- 真正的滚动窗口化是独立的渲染改造，需要覆盖展开折叠、拖拽、焦点、测高和滚动恢复。本轮实施的是完成状态局部更新与原渲染窗口保留，不是长列表 DOM 数量上限或虚拟列表改造。
- 下一阶段应在思源真实清单中验证尾部完成操作、快速连点、回滚、父子联动及分组变化，记录长任务和滚动位置，再决定哪些高频列表需要真正的可见窗口。继续使用当前状态源与 DOM 交互协议，不照搬整个 PINCH 框架。
- 同源 Web Locks 不是跨设备同步事务；最终 JSON 仍整文件读写。源文件测试通过也不代表已部署到思源，需要单独构建、安装后验证实际负载。
