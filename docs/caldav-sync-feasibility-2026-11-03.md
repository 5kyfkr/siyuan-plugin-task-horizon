# CalDAV 日历同步可行性评估

评估日期：2026-11-03。目标：Task Horizon 任务管理器接入 NAS 自建 CalDAV、iCloud 日历，并支持苹果和安卓客户端。当前确认范围是：复用现有 ICS 输出的数据量和内容，增加 VEVENT 单向 CalDAV 上传。Pinch 功能清单、VTODO 和双向内容保留作为参考，不作为当前开发范围。

现有“ICS 订阅”入口更名为 **ICS 上传**；新增入口名称确定为 **CalDAV 上传**：在“时间”分类中，位于“ICS 上传”下方，点击切换到同级独立设置页。

## 结论

建议增加。现有 ICS 数据收集、文档分组范围、提醒转换、发布调度和网络代理可以复用，协议接入的基础已经具备。方案确定为：**现有 ICS 的事件快照 → 逐条 VEVENT 资源 → 单向上传 CalDAV**。数据来源、数量边界、内容开关、重复实例和完成过滤都沿用现有 ICS。

推荐先用 NAS 作为统一服务端，苹果日历直接添加 NAS 的 CalDAV 账户，安卓通过 DAVx⁵ 同步到兼容的日历 App。苹果日历可以显示 NAS 日历，因此这条路径不要求再把 NAS 日历复制到 iCloud。iCloud 可作为另一种服务端选择。

当前无需补齐 Pinch 的全部选项，也无需增加 VTODO、优先级/待办状态字段或另一套重复任务推算。完成后推进、打卡和 FSRS 沿用现有 ICS 已有的事件表达，不回写本地任务。

## 当前确认范围

| 项目 | 当前范围 |
| --- | --- |
| 数据来源 | 现有 ICS 收集的日程，以及按现有开关选择的任务日期、番茄提醒、个人休息日 |
| 数据量 | 使用同一日期窗口、分组范围、过滤、重复展开和数量上限；不新增全任务扫描或无日期任务 |
| 事件内容 | 现有标题、起止时间、全天/跨日、可选备注、提醒、来源分类及已有完成标记 |

| 新增配置 | 独立的“CalDAV 上传”设置页，包含上传开关、地址、认证、发现并选择目标日历及上传结果 |

验收以“同一设置、同一时刻的完整数据快照”为准：CalDAV 托管事件与 ICS 输出在逻辑条目和业务内容上对应。UID、生成时间及托管属性属于协议适配，不能按文件字节完全相等验收。已不在完整输出集合中的旧托管资源，经映射和归属核验后清理；读取失败或结果截断不触发清理，其他日历条目不参与对账。

## 两个参考插件分别做了什么

### Pinch：单向上传，远端读取用于对账

核心流程见 [calendarSync.ts:95](https://github.com/royc01/pinch/blob/8b2b1b938d2804da0c76b757629b763a9a260527/src/calendarSync.ts#L95)：

1. 读取本地任务，展开窗口内的重复实例，转换成 VEVENT 或 VTODO。
2. 发现日历，读取带 `X-PINCH-MANAGED:TRUE` 的远端资源。
3. 按 UID 匹配，以 `X-PINCH-FINGERPRINT` 判断是否上传。
4. 新增或修改所需资源，删除远端仍存在而本次目标集合中已不存在的托管资源。
5. 由任务变动、防抖、定时和窗口恢复等入口触发。

**读取远端清单不等于双向同步。Pinch 没有把远端标题、日期或完成状态导入本地任务。** 外部编辑可能被忽略，之后的本地更新也可能覆盖外部编辑；外部删除后，本地仍存在的任务会在后续对账时重新上传。

它已支持 VTODO：截止日期、优先级、四种状态和完成时间；VEVENT 模式则过滤已关闭任务。其两种格式不是完全相同的数据集合。映射实现见 [calendarEventMapper.ts:172](https://github.com/royc01/pinch/blob/8b2b1b938d2804da0c76b757629b763a9a260527/src/utils/calendarEventMapper.ts#L172)。

值得参考：明确本地主导、稳定任务标识、托管标记、逐资源上传、语义比较、事件/待办两种表示。

需要重新设计的点：

- 删除不能只依赖“本次结果中没有”。当前任务管理器存在分组、滚动日期窗口、完成过滤和插件桥接读取失败，必须区分这些情况与真实删除。
- 远端保存的 fingerprint 不能替代实际字段对比；其他客户端可能保留旧 fingerprint，同时改了标题和时间。
- [calendarDavClient.ts:393](https://github.com/royc01/pinch/blob/8b2b1b938d2804da0c76b757629b763a9a260527/src/calendarDavClient.ts#L393) 的底层写入函数对非 2xx 直接抛错，而上层在返回后判断 412 再重试。按当前源码和本地包的静态控制流，这个 412 重试分支不可达。应独立实现并验证冲突处理。

### siyuan-plugin-caldav-sync：完整同步引擎，另有任务块映射

它维护独立的日历/待办 store，包含 `href`、`etag`、`dirty`、`deleted`、ICS 原文和同步 token；支持发现、增量拉取、脏条目上传、删除和冲突策略。编辑时尽量在原 ICS 上修改，保留未管理的属性。

当前源码还增加了思源原生任务块与 VTODO 的三方对账：块 ID 作为身份锚点，本地缓存作为上次同步基线，完成态可回写文档。不能只依据项目首页，将它理解成与笔记完全无关的独立日历。见 [block-sync.ts](https://github.com/vilifetime/siyuan-plugin-caldav-sync/blob/00760ce288360c73ca1055a6e2e3a084b80ca191/src/core/block-sync.ts) 与 [映射说明](https://github.com/vilifetime/siyuan-plugin-caldav-sync/blob/00760ce288360c73ca1055a6e2e3a084b80ca191/docs/block-sync.md)。该说明仍带有“尚未发版”字样，实际发布状态和完整兼容性不能单凭文档断言。

值得参考的是职责划分、原文保留、基线对账、串行上传和 token 失效回退。其原生块直接写入方式不适合原样接入任务管理器：本插件已经有统一任务写入服务和循环完成事务。

许可也需要区分：Pinch 的 LICENSE 为 MIT；此插件的 [LICENSE 为 AGPL-3.0](https://github.com/vilifetime/siyuan-plugin-caldav-sync/blob/00760ce288360c73ca1055a6e2e3a084b80ca191/LICENSE)，但同一提交的 [package.json 仍标 MIT](https://github.com/vilifetime/siyuan-plugin-caldav-sync/blob/00760ce288360c73ca1055a6e2e3a084b80ca191/package.json)。当前任务管理器为 MIT。不能根据 package.json 就把该项目代码当作 MIT 直接合入；建议基于标准独立实现，或在计划复用具体代码前厘清许可。复用 Pinch 的实质代码则需保留其 MIT 声明。

## 你的设备组合

| 组合 | 日历事件 VEVENT | 待办 VTODO | 建议 |
| --- | --- | --- | --- |
| NAS CalDAV → 苹果日历 | 可行，需实际验证具体服务 | 苹果日历事件显示不能代替待办客户端 | 首选事件模式 |
| NAS CalDAV → 安卓日历 | 可行，通常经 DAVx⁵ 接入 Android Calendar Provider | 需要兼容任务的客户端/存储提供方 | 首版验收安卓事件链路 |
| iCloud → 苹果日历 | 可行 | 新版 iCloud 提醒事项不开放标准 CalDAV 待办接口 | 使用 VEVENT |
| iCloud → 安卓日历 | DAVx⁵ 有 iCloud 日历接入支持 | 同样受 iCloud 提醒事项限制 | 可作为备用方案实测 |

依据：[苹果支持添加 CalDAV 账户](https://support.apple.com/zh-cn/guide/iphone/iphc37be2016/27/ios/27)、[DAVx⁵ 的 Android 集成说明](https://manual.davx5.com/introduction.html)、[DAVx⁵ 的 iCloud 支持及提醒事项限制](https://www.davx5.com/tested-with/icloud)。

iCloud 接入可采用 Apple 账户和 App 专用密码；生成专用密码要求账户启用双重认证，重置主密码会撤销专用密码。见 [Apple 官方说明](https://support.apple.com/zh-cn/102654)。

NAS 需确认具体服务软件、日历集合路径、认证和证书，以及思源所连接的内核能否访问该地址。内核代理从思源内核所在机器发请求；思源运行在远程服务器时，代理看到的局域网不一定是手机当前的局域网。

同步时效由插件运行、服务端和手机拉取共同决定。思源关闭或移动端被系统挂起期间，本地任务改动不会由插件持续上传；已上传的事件仍由手机日历管理和提醒。CalDAV 接入本身不保证秒级推送。

## 现有能力与缺口

| 层 | 已有基础 | CalDAV 需要增加/调整 |
| --- | --- | --- |
| 数据收集 | [buildCalendarSubscriptionEvents](../calendar-view.js#L41207)：日程、任务日期、番茄提醒、个人休息日 | 保留源 ID、实例 ID、字段版本和读取完整性；供逐条对账使用 |
| 同步范围 | [tmResolveCalendarSubscriptionScope](../src/task-horizon/main/task-runtime/53c-document-loader-runtime.js#L365)：分组并集、排除和当前块归属 | 可复用；显式标记范围配置变化 |
| ICS | [calendar-subscription-core.js](../calendar-subscription-core.js#L115)：转义、UTF-8 折行、时区、全天和 VALARM | 单资源序列化、托管属性、稳定修改时间；后续增加 VTODO |
| 网络 | [forwardCalendarSubscriptionRequest](../calendar-view.js#L41593)：内核代理和自定义头 | 日历发现、XML 多状态解析、REPORT、逐条 PUT/DELETE、ETag |
| 发布调度 | [现有发布运行时](../calendar-view.js#L41813)：快照检查、超时、防抖、取消、语义 hash | 独立 CalDAV 状态与逐条成功回执；适配后台启动和卸载 |
| 任务写入 | [__tmTaskMutations](../src/task-horizon/main/20-api-and-runtime-services.js#L8603) | 双向阶段统一由该入口回写，复用完成事务 |

CalDAV 不能只是把现有总 ICS 文件 PUT 到“另一个 WebDAV 地址”：不同 UID 必须存为不同资源，同一重复系列的组件应放在同一资源；资源不应带 METHOD。见 [RFC 4791 §4.1](https://www.rfc-editor.org/rfc/rfc4791.html#section-4.1)。

本项目当前还有几个直接影响方案的细节：

- 日程的 `uidSeed` 是 `schedule:<id>:<startAt>`（[41314 行](../calendar-view.js#L41314)），改开始时间会改变 UID。普通日程应改用稳定日程 ID；重复实例需要稳定的原始实例键，不能拿编辑后的开始时间当身份。
- 任务日期读取当前传入 `excludeCompleted:true`（[41359 行](../calendar-view.js#L41359)），输出也没有完整优先级/状态字段。VTODO 应从任务模型补充字段，不能只把 VEVENT 标签替换成 VTODO。
- `completionTime` 在本插件表示截止日期，真正完成时间是 `taskCompleteAt`；映射时必须分别对应 DUE 与 COMPLETED。
- 现有 ICS 固定 `Asia/Shanghai` 并附带 VTIMEZONE。可用于当前中国时区场景；跨时区增强需要单独设计，不能写 TZID 却遗漏对应时区定义。
- 现有范围是过去 30 天至未来约 400 天，事件总数上限 20,000。若直接展开为 CalDAV 资源，首次就可能有大量请求；应限制同步窗口、展示进度，并只上传变动项。
- 发布监听会响应乐观、提交和回滚阶段。CalDAV 上传应等待相关任务写入持久化，避免把随后回滚的状态写到外部。
- 公共 `queryTasks()` 有数量上限及 `partial/truncated` 语义，不宜作为完整同步数据源。应复用内部完整范围查询和投影。

## 建议的首版设计

设置入口沿用现有同级子页切换结构：

```text
设置 → 时间
         ICS 上传
         CalDAV 上传
```

“CalDAV 上传”紧接在“ICS 上传”下方，点击后右侧显示其独立设置页。页面采用现有原生表单、按钮和主题样式；桌面与移动端复用现有设置导航。

| 页面内容 | 控件和行为 |
| --- | --- |
| 启用 CalDAV 上传 | 独立开关；启用时显示连接配置 |
| 服务地址、用户名、密码 / App 专用密码 | 原生输入框，密码采用密码框 |
| 目标日历 | “发现日历”同时完成连接校验，返回支持 VEVENT 的可写候选集合，用户选择目标 |
| 上传方式 | 自动 / 手动，与现有 ICS 模式一致，取值独立保存 |
| 上传范围和内容 | 复用现有 ICS 的同一组数据设置及渲染片段，并说明两页共用；无需启用 ICS 文件上传即可调整和使用 |
| 立即上传、最近结果 | 一个主动上传按钮；显示运行状态、最近成功时间、条目数量或失败原因 |

CalDAV 可单独启用，也可与 ICS 发布同时使用。两者分别保存认证、启用开关、上传方式、成功回执和错误；关闭 ICS 文件发布不会阻止 CalDAV 读取公共数据。建议专用日历承载任务管理器导出的事件。

实现保持三层即可：现有数据收集适配、独立 CalDAV 客户端、同步协调器。无需引入另一套任务 store 或重新制作日历视图。

## 简洁性与维护边界

在当前“数据等同 ICS、VEVENT 单向、一个目标日历”的范围下，方案可以保持简洁。主要维护量来自 CalDAV 的资源身份、条件写入和删除核验，属于上传正确性所需的部分。

1. **一份数据收集逻辑。** 将现有事件快照读取整理为可复用的只读入口，ICS 与 CalDAV 调用同一实现。快照完整性校验、来源开关、范围和重复实例统一维护。
2. **两个输出通道。** ICS 继续生成集合文件；CalDAV 以同一快照生成逐条资源。各自保存目标及逐次结果，避免一个通道的成功 hash 让另一个通道误判为已经上传。
3. **一个专用客户端和一个协调器。** 客户端处理发现、XML、HTTP 和 ETag；协调器处理差异、运行状态与失败恢复。它们只读本地任务，对外上传，不进入任务写入事务。
4. **复用触发与生命周期。** 任务/日程变化、思源同步完成和日期边界沿用已有事件入口；按通道检查是否启用、是否自动及是否正在运行，分别取消和清理。上传功能由后台初始化，设置页只负责配置，不以打开设置页或日历视图作为运行条件。
5. **设置页使用既有路由。** 在 [TM_SETTINGS_V3_SUBPAGES](../src/task-horizon/main/settings/68-settings-v2.js#L25) 的 `c-ics` 后增加 `c-caldav`，将 `calendar-caldav` 设置区域路由到该页；同步维护 [设置区段索引](../src/task-horizon/main/task-runtime/53-list-render-and-document-loader.js#L6389)、搜索、定位及中英文标签。页面绑定归独立的 CalDAV 设置入口，不把网络请求塞进导航切换函数。

实施验收补充：ICS 关闭但 CalDAV 开启时可以上传；两通道分别启停且结果独立；进入/退出设置页不重复绑定上传监听；相同快照得到相同的逻辑事件集合；桌面和移动端都能从“ICS 上传”下方切换进入“CalDAV 上传”。

不需要引入通用账户平台、全新同步框架或第二套任务数据库。现有发布函数中依赖 `icsEnabled` 的运行检查应留在 ICS 通道，公共快照入口只处理数据读取与完整性。

每轮流程：等待持久化并读取完整快照 → 发现/校验目标集合 → 获取远端托管资源 → 按逻辑身份和业务内容比较 → 逐条创建/修改 → 核验删除候选 → 保存成功回执。

必须同时落实：

1. **稳定身份和归属。** UID 与资源名由稳定源 ID 派生；ICS 写入托管标记、工作区/同步配置命名空间、源类型和实例标识。仅修改属于本配置的资源；配置缓存丢失后可据此重建关系。
2. **条件写入。** 新建用 `If-None-Match:*`，修改/删除用 ETag。412 保留为冲突，重新读取并按单向策略处理；不把失败记成成功，也不默认无条件覆盖无法确认归属的内容。
3. **完整性和删除。** 查询失败、结果截断、插件桥接未就绪时停止删除。以现有 ICS 的完整输出集合为准，区分滚出窗口、同步分组变化、完成过滤、清日期和真实块删除；旧托管条目不再属于完整输出时，经源映射与归属核验后清理，不额外积累 ICS 范围外的历史。不能以任务界面的临时筛选结果或一次不完整读取判定清理。
4. **逐条结果持久化。** 每条确认成功后才更新其 ETag 和基线；中途失败可在下一轮重新对账。上传已到达而响应丢失时，按稳定地址读回确认；不能换随机 UID 重建。
5. **内容比较。** hash 只包含业务字段，排除每轮生成的 DTSTAMP 等易变值。保留创建时间，业务变更时更新修改时间；对已托管远端内容也检查实际字段/ETag，不能只信自报 fingerprint。
6. **设备并发。** 首版建议只在指定设备启用自动写入；其他设备默认不自动推送。进程内 running 标记不能协调两台电脑。启用推送前等待思源共享数据完成同步，避免旧快照覆盖新内容。
7. **格式与表示。** 全天 DTEND 使用排他结束日；有时间事件保存明确时区或等价 UTC。提醒、完成过滤和完成标记均沿用现有 ICS；不增加新的任务状态映射选项。VEVENT 没有待办式的完成状态语义。

重复日程和任务实例直接复用现有 ICS 输出，补充逐资源管理所需的稳定身份，不增加新的展开算法或未来实例。任务日期、关联日程和番茄提醒是不同来源角色，按现有开关选择，不能靠标题合并。

## VTODO 和双向的额外成本（当前范围外）

VTODO 单向阶段补充 DTSTART、DUE、PRIORITY、STATUS、PERCENT-COMPLETE、COMPLETED。按本插件实际状态/marker 规则映射，支持无日期待办；目标集合须确认支持 VTODO，客户端也要能展示待办。

双向阶段至少要保存上次同步基线，比较本地、服务端、基线三者，区分单端修改与真正冲突；还要确定外部新建任务落在哪个文档、外部删除是否允许删除笔记、哪些字段允许回写、外部事件与本地任务的绑定规则。

普通独立日程的标题/时间回写，和任务 VTODO 的状态回写，应分开验收。任务回写必须经过现有 MutationService；原文合并需要保留参与人、时区和未知属性。

**循环任务完成尤其不能直接改 `done` 或 Markdown。** 当前 [完成计划](../src/task-horizon/main/task-runtime/54-recurring-task-runtime.js#L38) 涉及 `occurrenceId`、`operationId`、历史、下一轮、FSRS 和跨插件回执。外部同一条完成更新重复到达时只能消费一次；旧实例不能误完成新一轮，撤销也要指向正确历史。完整双向需要这一层协议适配，参考插件的布尔/四态块映射不足以替代。
